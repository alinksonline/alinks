1. PRODUCT DEFINITION (LOCKED)
--------------------------------------------------------------------------------
One-liner:
  ALINKS gives budget-strapped Indian startups a mobile-first mini-website and
  simple dashboard — up to 5 pages — so they get digital presence without
  spending lakhs on custom dev or agencies.

What it is:
  - A multi-tenant "mini website" platform (not a full website builder like Wix)
  - Optimized for MOBILE + TABLET viewing (primary)
  - Desktop viewing: supported but optional / secondary
  - Tenant dashboard to customize their public pages
  - Hard limit: MAX 5 PAGES per tenant (sufficient by design — not a limitation bug)

What it is NOT (scope guardrails):
  - Not unlimited pages / full CMS
  - Not a replacement for heavy custom ERP
  - Not Artix selling regulated goods directly — tenants run their own businesses;
    ALINKS provides the digital storefront tooling (compliance still applies)

PRIMARY AUDIENCE
  - Indian startups with low or zero marketing/dev budget

3B. APPOINTMENTS SCOPE (LOCKED — SALONS TO CLINICS, DOC–PATIENT)
--------------------------------------------------------------------------------
Founder intent: One appointments/booking system for ALL service-based businesses
that take bookings — from salons and beauty centers to clinics, doctors, and full
doc–patient scheduling. Same 5-page mini-site; booking widget adapts by sub-mode.

APPOINTMENT SUB-MODES (single engine, different templates + compliance tier):

  TIER 1 — Beauty & wellness (LOW regulatory friction)
    - Salons, barbers, beauty parlours, beauty centers
    - Spas, massage (non-medical), nail art, lash/brow, makeup artists
    - Tattoo studios, grooming lounges, bridal makeup
    - Fitness trainers, yoga/zumba, dance, music — 1:1 slots MVP; group batches Phase 2 (Q026)

  TIER 2 — Professional services (LOW friction)
    - Consultants, coaches, tutors (group class batches Phase 2 — Q026), photographers
    - Lawyers/architects (initial consult slot — not legal advice via platform)
    - Pet groomers, veterinary OPD (vet licensing — see Tier 3 lite)

  TIER 3 — Healthcare & clinical (HIGH friction — license gating + DPDP health data)
    - Clinics, polyclinics, hospitals (OPD appointment only)
    - Doctors: GP, specialists, dentists, dermatologists, pediatricians
    - AYUSH practitioners (Ayurveda, Homeopathy, Unani, Siddha — reg no. required)
    - Physiotherapy, chiropractic, mental health counsellors/psychologists
    - Diagnostic labs (sample collection slot booking — not report delivery MVP)
    - Doc–patient: patient picks doctor → picks slot → booking confirmed to both sides

DOC–PATIENT MODEL (what ALINKS provides vs what it does NOT)
  ALINKS PROVIDES (booking layer — not a hospital EMR):
    - Doctor/clinician profile pages (name, qualification, reg no., photo, timings)
    - Patient books slot with a specific doctor or "any available"
    - Patient details: name, phone, optional age/gender, optional visit reason
    - SMS/WhatsApp confirmation + reminder to patient and clinic dashboard
    - Clinic dashboard: today's appointments read from tenant Google Sheet
    - Mark completed/no-show → updates tenant's Sheet row (NOT Artix database)

  ALINKS DOES NOT PROVIDE (phase 2+ / separate legal review):
    - Electronic Medical Records (EMR), diagnosis, prescription writing
    - Telemedicine video consult inside ALINKS (NMC Telemedicine Guidelines 2020)
    - Lab report storage, vitals tracking, medicine orders
    - Replacing doctor–patient relationship — tenant clinician is always responsible

BEAUTY & SALON PACKAGES MODEL (LOCKED — PAY FIRST, THEN APPOINTMENT)
--------------------------------------------------------------------------------
Founder intent: For salons, beauty centers, barbers, spas, and similar Tier-1
businesses, customers browse PACKAGES (bundled services), pay online, then pick a
slot — payment + appointment are one flow.

CUSTOMER FLOW (salon / beauty — Pro tier)
  1. Customer opens tenant mini-site → Packages or Services page
  2. Selects a package (e.g. "Bridal Glow — ₹4,999" or "Haircut + Beard — ₹499")
  3. Pays via UPI/card/COD rules (tenant payment gateway)
  4. After successful payment → date/time slot picker opens
  5. Customer confirms slot → appointment auto-created and linked to payment
  6. WhatsApp/SMS confirmation with package name, amount paid, date/time
  7. Row appended to tenant Google Sheet (Appointments tab) — PAID + package details
  8. Salon dashboard reads appointment from their Sheet (not stored on Artix)

PRE-MADE PACKAGES (Artix library — 12 at launch, tenant can use or customize — Q023)
  ALINKS ships 12 ready-made package templates at launch: 6 salon + 6 beauty center.
  Tenant onboards → picks templates → use as-is OR customize name, price, duration,
  included services, photos — or create fully custom packages from scratch.

  Example pre-made salon packages (editable):
    - Basic Haircut (30 min, ₹199)
    - Haircut + Beard Trim (45 min, ₹349)
    - Hair Spa + Cut (90 min, ₹899)
    - Facial Classic (60 min, ₹599)
    - Bridal Package Full (240 min, ₹4,999)
    - Party Makeup (90 min, ₹2,499)
    - Manicure + Pedicure Combo (120 min, ₹1,299)

  Example pre-made beauty center packages (editable):
    - Clean-up + Bleach (60 min)
    - De-tan + Facial (90 min)
    - Pre-bridal 5-session bundle
    - Skin glow monthly pack (4 visits)

  Package fields (dashboard):
    - Name, description, image
    - Included services list (bullet items)
    - Total duration (auto-calculates slot length)
    - Price, optional discount/MRP display
    - Active/inactive toggle
    - Source tag: "ALINKS template" vs "custom"

  Tenant actions:
    [Use template] → copies pre-made package into their catalog
    [Edit]         → change price, services, duration, photos anytime
    [Create new]   → build custom package from scratch
    [Disable]      → hide package without deleting

  Clinics/doctors: packages optional (e.g. "Health checkup bundle") — Phase 2;
  MVP clinic flow remains slot booking; beauty/salon packages are priority.

APPOINTMENT FEATURES (Pro tier — draft)

5. COMPLIANCE PHILOSOPHY
--------------------------------------------------------------------------------
CORE LIABILITY PRINCIPLE (LOCKED — FOUNDER INTENT)
  "Any business they conduct is their headache, not ours."

  Artix / ALINKS is a technology platform (SaaS + hosting + tools). Tenants run
  their own businesses. All sector-specific legal duties — licenses, product safety,
  medical conduct, food standards, tax on sales, consumer disputes, refunds for
  salon packages or doctor visits — are the TENANT'S responsibility, not Artix's.

  The platform must SAY this clearly in lawyer-drafted legal documents and enforce
  it in product (checkbox at onboarding, footer links, tenant storefront disclaimer).

TIER A — MUST HAVE (before public launch in India)
  - Artix entity registered (proprietor + MSME now → Pvt Ltd before public launch)
  - Platform Privacy Policy (Artix — how ALINKS handles platform user data)
  - Platform Terms of Service (Artix — tenant + end-customer facing sections)
  - DPDP Act 2023: consent, data rights, breach process, grievance officer
  - IT Act intermediary compliance: due diligence, takedown workflow
  - GST on ALINKS subscriptions (SaaS, likely 18%)
  - Tenant is seller / service provider of record for ALL tenant business activity
  - Consumer Protection Act: clear ALINKS subscription cancellation & refund policy
  - Secure auth, HTTPS, encryption at rest for sensitive fields
  - Content moderation for illegal/prohibited listings

TIER B — STRONG RECOMMENDATION
  - Lawyer-drafted documents (NOT copy-paste templates) — see Section 5C
  - Tenant onboarding: must accept Platform ToS + acknowledge tenant liability
  - Tenant-facing Privacy Policy template they publish on their mini-site
  - Tenant Terms template for THEIR customers (salon refund rules, shop returns, etc.)
  - Razorpay / Cashfree for subscription billing only (Artix revenue)
  - Separate "tenant payments" model: connected accounts OR tenant brings own PG
  - Audit logs (admin actions, billing, page publishes)
  - Limitation of liability + indemnity from tenants for their content/sales/services
  - Storefront footer on every tenant site: "Powered by ALINKS" + link to platform ToS
    + "This business is operated independently by [Tenant Name]"

TIER C — AVOID / HIGH RISK
  - Enabling prescription drug sales without verifying drug licenses
  - Processing tenant customer payments without clear legal role (marketplace vs SaaS)
  - Storing Aadhaar/PAN without purpose limitation
  - Auto-renew subscriptions without clear consent (Consumer Protection / dark patterns)
  - Claiming ALINKS "is" the pharmacy/restaurant — always tenant-branded
  - Ignoring FSSAI display requirements for food tenants
  - Affiliate links without disclosure (#ad / sponsored — ASCI guidelines)
  - Telemedicine / video consult / e-prescription without NMC + drug rules compliance
  - Storing clinical diagnoses or lab reports as if ALINKS is an EMR
  - Building a client/customer/patient CRM database on Artix PostgreSQL
  - Retaining end-customer PII after successful Google Sheet write
  - Allowing unverified "doctors" without registration number check
  - Artix implying it endorses, employs, or guarantees any tenant's services
  - Hiding platform liability disclaimers to look like Artix runs the shop/clinic

AI/ML PIPELINE (ALINKS Verify — build in Phase 2, basic rules Phase 1.5)

    - Manual fallback queue if no online registry for that state
    - Pharmacy: state drug controller format validation

  Step 5 — Risk score (0–100)
    - High confidence + all checks pass → AUTO_APPROVE (target 80%+ of applications)
    - Medium confidence → PENDING_REVIEW queue (junior mod or Benjamin batch review)
    - Low confidence / mismatch / duplicate → REJECT with reason + re-upload option

  Step 6 — Audit log (Artix protection)
    - Store: upload hash, OCR result, risk score, auto vs human decision, timestamp
    - If sued: "We verified license [reg] with automated + human review on [date]"

1) DATA RETRIEVAL — WILL IT BE FAST?
--------------------------------------------------------------------------------
Honest answer: Google Sheets API is slower than a local database, but fast enough
for small businesses if we design smart reads. Target: dashboard feels < 1 second.

Typical Google Sheets API latency:
  - Single tab read (today's rows):     200–600 ms
  - Batch read (3 tabs at once):        400–900 ms
  - Append one row (booking):           300–700 ms
  - Cold start / token refresh:         +1–2 s occasionally

SPEED STRATEGY (how we make it feel fast)
  a) SHORT-LIVED CACHE (Redis, TTL 2–5 minutes — NOT permanent storage)
     - Cache key: tenant_id + business_id + tab + date_range
     - On dashboard open: show cached data instantly → refresh in background
     - "Last updated 2 min ago" + manual Refresh button
     - Founder approved this in session 7

  b) READ ONLY WHAT'S NEEDED
     - Default view: TODAY + NEXT 7 DAYS appointments (not entire sheet history)
     - Orders: last 30 days paginated (50 rows per page)
     - Use Google API filters / row ranges (A1 notation) — never load 10,000 rows

  c) BATCH API CALLS
     - One network call fetches Appointments + Orders + Customers summary
     - Avoid 3 separate round-trips

  d) OPTIMISTIC UI ON WRITES
     - Customer books → show success immediately after Google append confirms
     - Dashboard pending row: "Syncing…" until read confirms (usually < 2 s)

  e) BACKGROUND PREFETCH
     - When tenant opens dashboard, prefetch in parallel with page editor load

  f) SLA EXPECTATION (set with tenants)
     - "Dashboard reflects new bookings within 1–2 minutes" — honest marketing
     - Not millisecond HFT — fine for salon, kirana, clinic OPD

WHEN IT WON'T BE FAST (edge cases — tenant should know)
  - Tenant has 50,000+ rows in one tab → suggest archive tab or export
  - Google outage → dashboard shows cached data + warning banner
  - Tenant on 2G → slow regardless; mini-site booking still works (write is async)

PERFORMANCE TARGETS (engineering goals)
  | Action                    | Target perceived time |
  |---------------------------|----------------------|
  | Dashboard open (cached)   | < 300 ms             |
  | Dashboard refresh (live)  | < 1.5 s              |
  | New booking appears       | < 3 s after submit   |
  | Mark appointment done     | < 2 s                |

5G. REDIS SPEED LAYER (LOCKED — FOUNDER APPROVED "AWESOME IDEA")
--------------------------------------------------------------------------------
Founder intent (session 9):
  "We can use Redis — that's really an awesome idea. Redis will cover for speed,
   correct?"

ANSWER: YES — Redis is the speed layer. It does NOT store client data permanently.
It makes Google Sheets / Supabase backends feel instant for tenants and customers.

WHAT REDIS IS (in ALINKS architecture)
  - In-memory cache sitting between ALINKS app and slow external APIs (Google Sheets)
  - Also speeds up: public mini-site page loads, product catalog, share card generation
  - Hosted: Upstash Redis (serverless, Mumbai region) OR Redis on same VPS as app
  - Artix-owned Redis — contains ONLY short-lived cached copies + session data
  - NEVER the system of record for client PII (Google/Supabase remain source of truth)

WHAT REDIS CACHES (and TTL)
  | Cache key type              | TTL        | Purpose                          |
  |-----------------------------|------------|----------------------------------|
  | Dashboard appointments    | 2–5 min    | Today's bookings from Sheets/DB  |
  | Dashboard orders            | 2–5 min    | Recent orders list               |
  | Customer tab summary        | 5 min      | Row count + last 10 (not full CRM)|
  | Public product catalog      | 10–15 min  | Shop page fast load on 4G        |
  | Single product page         | 15 min     | Product detail + OG share image  |
  | Package list (salon)        | 10 min     | Packages page render             |
  | Share card image (generated)| 24 hours   | Pre-rendered PNG/WebP per product|
  | Tenant page content (pub)   | 5–10 min   | 5-page mini-site HTML/data       |
  | Rate limit counters         | 1 min–1 hr | Abuse prevention                 |
  | OTP / session tokens        | 5–15 min   | Auth (tenant login only)         |

HOW REDIS MAKES IT FEEL FAST (stale-while-revalidate pattern)
  1. Tenant opens dashboard
  2. Redis HIT → show data in < 100 ms (feels instant)
  3. Background job fetches fresh data from Google/Supabase
  4. If changed → update Redis + subtle UI "Updated just now"
  5. If Google slow/down → keep serving Redis + yellow banner "Using cached data"

  Customer opens product link from WhatsApp:
  1. Product page served from Redis-cached catalog → fast first paint
  2. Share OG image already in Redis/CDN → pretty link preview in WhatsApp

WRITE PATH (booking/order — Redis role)
  - Write goes DIRECTLY to Google Sheet or Supabase (source of truth)
  - On successful write → INVALIDATE relevant Redis keys immediately
  - Next dashboard read → cache miss → fresh fetch → repopulate Redis
  - Optional: write-through — update Redis with new row after Google confirms

REDIS DOES NOT REPLACE GOOGLE / SUPABASE
  | Concern                         | Answer                                |
  |---------------------------------|---------------------------------------|
  | Redis covers speed?             | YES for reads + page loads            |
  | Redis stores client data forever?| NO — TTL expires, keys deleted       |
  | If Redis crashes?               | App fetches from Google/Supabase direct|
  | Is client data safe in Redis?   | Ephemeral copy only; encrypted transit|
  | Supabase tenants need Redis?    | Less critical (DB is fast) but still  |
  |                                 | helps catalog + share cards + pages   |

SECURITY
  - Redis keys namespaced: tenant_id:business_id:resource — no cross-tenant leak
  - No long TTL on PII-heavy keys (max 5 min for appointment rows with phone)
  - Redis not exposed to public internet (private network / Upstash TLS)
  - Client phone numbers in Redis cache: acceptable as ephemeral (same as in-flight)

INFRASTRUCTURE (draft)
  - MVP: Upstash Redis (pay-per-request, Mumbai, ~$10–30/mo at early scale)
  - Scale: Redis Cluster or ElastiCache when 10k+ tenants
  - Monitor: cache hit rate target > 80% on dashboard reads
